# Plan: F90 modules and `IMPLICIT NONE`

Written 2026-10-13, after the COMMON-block consolidation closed. It assumes
no familiarity with that work beyond what is recorded in
`KNOWN_ISSUES.md`.

## Objective

1. Replace the 86 remaining `COMMON` blocks with F90 modules.
2. Bring every scoping unit to `IMPLICIT NONE` with explicit declarations.

## Why in that order

The two jobs look separate but are not. 42,504 names currently have no
explicit type declaration, and they split sharply:

| | count | handled by |
|---|---|---|
| COMMON members | **32,351** | the module conversion -- 861 declarations, written once each |
| locals and dummy arguments | **10,153** | genuine per-routine work |

A member typed once in a module needs no declaration in any file that
`USE`s it, so **doing modules first removes about 76% of the
implicit-typing burden**. What remains is 10,153 names at a median of 34
per file.

## What has been verified, not assumed

Tested on this machine with the Makefile's own flags, so the plan does not
rest on recollection:

- **No compiler restricts fixed-form source to F77.** `gfortran`,
  `ifort` 2021 Classic and `ifx` 2024.2 all compiled a fixed-form `MODULE`
  and a legacy routine that `USE`s it, return code 0. The `.f` extension
  selects fixed form, nothing about language level.
- **A single routine can `USE` a module and still declare `COMMON`.** This
  is what makes an incremental, block-by-block conversion possible.
- The codebase already uses F90-era spellings: inline `!` comments, names
  well past six characters (`TOL_CZBASE_FINE_WIDTH`), underscores,
  lowercase, and `&` as a column-6 continuation marker.
- **`DATA` cannot initialize a `USE`-associated variable.** gfortran:
  `Error: Cannot change attributes of USE-associated symbol codm`. This is
  a hard constraint, not a style preference -- see stage 2.
- **`.mod` files are compiler-specific.** `ifort` on a gfortran-written
  `.mod`: `error #7013: This module file was not generated by any release
  of this compiler`.
- **`ifort`/`ifx` `-warn all` already enumerate the implicit-typing work**,
  as warning `#6717: This name has not been given an explicit type`, even
  where an `IMPLICIT REAL*8(A-H,O-Z)` is in force. Counts land within ~5%
  of an independent static estimate (`coefft.f` 506 against 529,
  `seculr.f` 414 against 455), so the compiler can produce the
  authoritative per-file, per-line list and no custom tooling is needed.

## Stage 0 -- build system

**Status: done on 2026-10-14, except item 3, which is deliberately
deferred until a module first `USE`s another.**

What landed: `MODOBJS` (sources named `*_mod.f` by convention) built ahead
of `OBJS` via an `$(OBJS): $(MODOBJS)` dependency, `OBJS` narrowed with
`filter-out` so module objects are not listed twice, `*.mod` and
`$(MODOBJS)` added to `clean`, and the `.mod` directory stated explicitly
for all three compilers (`-J.` for gfortran, `-module .` for ifort and
ifx).

**Pitfall found while testing, worth remembering.** The ordering rule was
first placed next to the `OBJS` definition near the top of the file. The
first target in a makefile becomes make's default goal, so that silently
redefined a bare `make` to build `chkscal.o` and stop -- it reported
"Nothing to be done" and left the binary untouched, which is easy to
mistake for an up-to-date tree. The rule now sits with the other targets,
and `.DEFAULT_GOAL := default` is pinned so a future rule added above
cannot do the same thing again. Any new rule in this file belongs below
the targets section.

Verified three ways: a scratch tree whose module sorts alphabetically last
(`zz_mod.f`) and whose user sorts first (`aaa.f`) fails under the old rule
with exactly the predicted `Can't open module file` error and builds and
runs under the new one, both serially and under `make -j4`; and a full
`make clean && make` of the real tree rebuilds without error and gives
outputs byte-identical to the references on three cases.

The original finding, for the record. `Makefile:40` was

```make
OBJS := $(patsubst %.f,%.o,$(wildcard *.f))
```

with no dependencies between objects, so files compile in alphabetical
order. A module must be compiled before anything that `USE`s it, and the
failure is immediate and loud:
`Fatal Error: Can't open module file 'nmlpar_mod.mod' for reading`.

1. **Done.** Add a `MODOBJS` list compiled ahead of `OBJS`. Sufficient
   while modules are few and do not `USE` one another.
2. **Done.** Add `*.mod` to the `clean` target. It removed only `$(NAME)`
   and `$(OBJS)`, so a stale `.mod` survived -- and a `.mod` from another
   compiler produces the confusing `#7013` above. This had to land before
   the first module.
3. **Deferred by design.** When modules start depending on each other,
   move to generated dependencies (`makedepf90` or a short script) as a
   make prerequisite. The current rule orders modules against ordinary
   objects but not against one another, so the first module that `USE`s
   another is the trigger for this item. Until then it would be
   unexercised machinery.
4. **Done.** The `ifort`/`ifx` branches both honour `-module <dir>`, now
   set explicitly alongside gfortran's `-J.`.

## Stage 1 -- pilot, one module end to end

**Status: done on 2026-10-14.** `COMMON/RUNLOOP/` is now `RUNLOOP_MOD` in
`runloop_mod.f`, imported by all ten files that declared the block.

It was the right pilot: 4 members, 10 files, no `DATA` initialization, and
per-run-loop control rather than hot-path physics.

### The pattern other stages copy

1. **File and module naming.** One block per file, `<block>_mod.f` holding
   `MODULE <BLOCK>_MOD`. The `_MOD` suffix keeps module names clear of
   routine names, and the `*_mod.f` glob is what the Makefile's `MODOBJS`
   matches, so a new module needs no Makefile edit.
2. **`USE ... , ONLY:`, naming only the members the routine references.**
   This is the decision worth keeping. A blanket `USE` imports every name
   in the block, which is precisely the hazard the `RL`/`RLL` rename had to
   pre-empt; `ONLY` makes that class of collision impossible and documents
   what each routine actually touches. Six of the ten files here use a
   strict subset, so the lists carry real information:

   | file | imports |
   |---|---|
   | `chkcal.f`, `rscale.f` | `RESCAL` |
   | `starin.f`, `wrthead.f` | `IRESCA` |
   | `htimer.f` | `LENDAG, LSETDT` |
   | `chkscal.f` | `RESCAL, LENDAG` |
   | `main.f` | `RESCAL, IRESCA, LENDAG` |
   | `parmin.f`, `setcal.f`, `setscal.f` | all four |

   For a very large block the list gets unwieldy -- `NMLPAR` has 234
   members across 121 files -- but it is mechanical to generate from actual
   usage, and the generated list is the useful artifact. **Decide this for
   `NMLPAR` before Stage 2 starts**; the fallback is a blanket `USE` there
   and `ONLY` everywhere else, accepting that the big block reserves 234
   names in every routine that imports it.
3. **Where the `USE` goes, and why this is not a substitution in place.**
   `USE` must be the first thing in the specification part, ahead of
   `IMPLICIT`, so the statement cannot simply replace the `COMMON` line
   where it stood. It goes immediately after the program-unit header and
   all of that header's continuation lines. `main.f` is the awkward case:
   it is a main program written with no `PROGRAM` statement, so the `USE`
   becomes the unit's first statement, ahead of its `PARAMETER`s.
4. **Explicit types, restating what the implicit rules gave.** The module
   declares `REAL*8`, `INTEGER*4` and `LOGICAL*4` to match
   `IMPLICIT REAL*8(A-H,O-Z)`, the default `INTEGER` rule for `I`, and
   `IMPLICIT LOGICAL*4(L)`. Writing them out is what makes Stage 5
   possible, and it can remove latent inconsistency: only `parmin.f`
   carried `IMPLICIT INTEGER*4(I,...)`, so `IRESCA` was default `INTEGER`
   in the other nine files and would have become `INTEGER*8` under
   `-fdefault-integer-8`, silently disagreeing with `parmin.f`.
5. **`SAVE` stated explicitly**, not relied on. Module variables are
   implicitly saved only from Fortran 2008 and `ifort` Classic predates
   it. A bare `SAVE` in the module covers every member and matches
   COMMON's semantics.
6. **Keep the block's history comment.** The 8-line note explaining what
   `RUNLOOP` is moved into the module, where it belongs, and each importer
   carries a short note pointing at it rather than a copy.

### On zero-initialization

Worth stating because the code relies on it: `COMMON` members land in
static storage and are zero-filled in practice, which this code depends on
in places -- `starin.f` calls `RSCALE` when `IRESCA(NK).NE.1`. A `SAVE`d
module variable is static storage too, so the behaviour is unchanged, and
`parmin.f:1454` sets `IRESCA` from the namelist per run in any case. For
blocks that genuinely depend on an implicit zero, consider an explicit
initializer in the module, which is legal there and makes the dependence
visible. Note that this is also the one thing that cannot be left in the
importing file: `DATA` on a `USE`-associated name is rejected outright
("Cannot change attributes of USE-associated symbol"), so a block whose
members are `DATA`-initialized must have that initialization moved into
the module.

### Test coverage of this stage, which is thinner than it looks

A compile proves the conversion is well formed; it does not prove the
routines run. Of the ten files, `parmin.f`, `starin.f`, `main.f`,
`htimer.f` and `wrthead.f` run in every case, and `rscale.f` runs whenever
`IRESCA(NK).NE.1`. But:

- `setcal.f` and `chkcal.f` sit behind `IF(LCALS)`, and exactly one case
  in the whole suite sets it:
  `examples/run_standard_solar_model/Test_solarcal_noGS_norot`. It is in
  the targeted set for that reason alone.
- `setscal.f` and `chkscal.f` sit behind `IF(LCALST)`, and **no case sets
  `LCALST`**. Their conversion is compile-checked only. This is the same
  kind of gap as `LADON`/`LACOUT` leaving the `ISOUND` write path
  unexercised, and it is worth recording whenever a stage touches a file
  the suite cannot reach.

## Stage 2 -- the consolidated blocks

The biggest single win, because these hold most of the 32,351 member names.

| block | members | files |
|---|---|---|
| `NMLPAR` | 234 | 104 |
| `NMLBYPASS` | 83 | 3 |
| `IOUNITS` | 29 | 58 |
| `CONSTANTS` | 30 | 90 |
| `RUNLOOP` | 4 | 10 |
| `INTPAR` | 3 | 3 |

**The `DATA` constraint governs this stage.** About 280 `DATA` statements
currently initialize COMMON members from inside `parmin.f` -- the namelist
defaults -- and roughly 200 of those are `NMLPAR` members, 83 `NMLBYPASS`.
Because `DATA` on a `USE`-associated variable is rejected, every one must
move into the module as an initializer at the moment its block converts.
That is mechanical, and it is also a standards improvement: `DATA` on a
COMMON member outside `BLOCK DATA` is non-standard today.

Blanket `USE` is safe here: the stage-2 collision scan established that no
file declaring one of these blocks has a local of the same name as any
member, and the two prefix declarations that would have broken it are gone.

## Stage 4 -- remaining blocks by category

Convert in the order of the existing classification, since it already
groups by lifetime and by who touches them: start-of-timestep (17),
output stores (8), rotation (7), then the set-aside blocks. Respect the
constraints already recorded -- in particular issue 7, where `QATM` and
`QENV` are invoked through `MMID`/`BSSTEP` with a fixed argument list, so
their data must keep travelling by module variable rather than becoming
arguments.

## Stage 5 -- `IMPLICIT NONE`

Only now, with roughly 10,153 names left at a median of 34 per file.

Per file: compile with `ifort -warn all` (or `ifx`), take the `#6717`
list, add explicit declarations, then add `IMPLICIT NONE` and rebuild so
the compiler enforces completeness. Heaviest first or lightest first as
preferred; the heavy ones are `starin.f` (289 after modules), `main.f`
(263), `parmin.f` (239), `wrtout.f` (207).

Two traps, from issue 6. Files currently lacking
`IMPLICIT REAL*8(A-H,O-Z)` give 4-byte reals, so a name that looks
harmlessly undeclared may already be single precision -- 16 scoping units
are in that state, and `IMPLICIT NONE` will expose rather than create the
question of which width was intended. And `IMPLICIT` is per scoping unit,
not per file: `alfilein.f` carries five `IMPLICIT` statements.

## Validation protocol

Unchanged from the consolidation work, which caught every regression at
the cheapest point:

1. Build with `gfortran`, and cross-check with `ifx` at stage boundaries.
   Treat any `size of symbol changed` warning as a hard stop while COMMON
   blocks remain.
2. Where signatures change, audit that every definition and call site agree
   on argument count. F77 has no cross-file interface checking, so this
   must be checked mechanically -- it is how the 24-against-23 argument
   mismatch in `CALL MDOT` was found.
3. Run the 17-case targeted set, extended with cases that exercise the
   specific path: TAHB cases for the high-Z EOS and opacity work,
   `LOPAL95` cases for OPAL95, `LSTCH` for `stitch.f`, the `m0p8` wind and
   solid-body rotators for rotation.
4. Full 298-case suite at each stage boundary, about five hours.
5. After a full run, restore the two m9p0 `.last` fixtures (issue 4).

## Risks

| risk | mitigation |
|---|---|
| Module compiled after its users | stage 0; failure is immediate, not silent |
| Stale or foreign `.mod` | `clean` removes `*.mod`; rebuild when switching compiler |
| `DATA` on a `USE`-associated variable | move all ~280 into the modules, per block, as it converts |
| Blanket `USE` importing a name a file uses locally | already scanned clean for the consolidated blocks; rescan per block before converting |
| Module name colliding with a routine name | `_MOD` suffix |
| `ifort` Classic is deprecated, discontinued late 2024 | prefer `ifx` for the Intel path; both verified working |
| Divergent member names under one module | issue 14, settle before stage 3 |
